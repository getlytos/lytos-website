## Vous développez avec l'IA ?

Vous changez de modèle. Vous ouvrez une nouvelle session. Vous passez de Claude à Codex.
Et chaque fois, le même rituel : il faut redonner le contexte, répéter les conventions, corriger les mêmes dérives.

Pendant ce temps, la dette s'installe. Le code généré aujourd'hui ne ressemble plus à celui d'hier. Les conventions glissent. Le projet grossit plus vite que la capacité de l'IA à s'y repérer.

Cette friction, beaucoup ont fini par l'accepter comme normale. Elle ne l'est pas.

**Lytos répond à ce problème en ancrant le contexte à l'endroit où il doit vivre : dans le repo.**

---

## Pour qui, pour quoi

| Profil | Setup typique | Ce que Lytos apporte |
|---|---|---|
| **Vibe-coder / maker** | Claude Code, Codex, apps IA + GitHub | Un manifest que l'IA lit à chaque session. Moins de réexplication, un contexte qui s'enrichit. |
| **Développeur** | IDE + Git (GitHub / GitLab) + IA en appoint | Règles versionnées, mémoire qui se construit, board qui trace le travail — dans le repo, pas dans un SaaS. |
| **Équipe** | IDE + Git + CI + revues + ticketing produit | Manifest, skills, rules partagés. L'IA produit dans le style du projet. Les specs techniques pour l'IA vivent dans le repo, à côté du code. |

## Les limites du paradigme sub-agents

La majorité des frameworks IA actuels vous proposent de déléguer à des agents : un agent "architecte", un agent "testeur", un agent "reviewer". Plus on délègue, moins on garde le fil. Le contexte s'éparpille plus facilement, les décisions deviennent plus difficiles à tracer.

**Lytos propose une approche complémentaire.**

> *"L'agile a structuré la collaboration humaine. Lytos essaie de structurer la collaboration avec l'IA."*

Pas d'agents autonomes. Pas de personas qui décident à votre place. L'IA reste un outil — puissant, mais dirigé. C'est vous qui définissez l'intention. C'est vous qui validez chaque étape. Le modèle exécute. Vous, vous gouvernez.

[Pourquoi l'approche sub-agents nous semble limitée →](/fr/method/sub-agents/)

## Votre contexte vous appartient

Avec les outils cloud classiques, votre contexte projet vit dans leurs serveurs, dans leurs formats, dépendant de leurs APIs. Changer de modèle signifie tout recommencer.

Avec Lytos, tout est en Markdown dans votre dépôt Git. Votre manifest, vos standards, votre mémoire de projet : version-contrôlés, portables, lisibles par n'importe quel modèle.

Aujourd'hui Claude. Demain GPT ou Gemini. Votre contexte ne bouge pas.

> *"Choisissez votre IA. Ne lui appartenez pas."*

[En savoir plus sur la souveraineté →](/fr/philosophy/sovereignty/)

## Opérationnel en 2 minutes

```bash
npm install -g lytos-cli
lyt init
```

<img src={lytBoard.src} alt="lyt board — Le kanban Lytos dans le terminal" style="border-radius: 2px; border: 1px solid var(--lytos-ink-12); margin: 1.5rem 0;" />

`lyt init` génère la structure complète dans votre projet : `manifest.md`, `skills/`, `rules/`, `issue-board/`, `memory/`. Tout en Markdown. Tout dans votre repo.

| Commande | Ce qu'elle fait |
|----------|----------------|
| `lyt init` | Génère `.lytos/` (interactif, détecte votre stack) |
| `lyt board` | Régénère le kanban board |
| `lyt lint` | Valide la structure `.lytos/` |
| `lyt doctor` | Diagnostic complet avec score de santé |
| `lyt show` | Détail d'une issue avec progression |
| `lyt start` | Démarre une issue — branche, board, tout en une commande |
| `lyt close` | Ferme une issue — done, board, vérifie la checklist |

[Voir toutes les commandes sur npm →](https://www.npmjs.com/package/lytos-cli)

## Fonctionne avec votre setup actuel

Lytos n'est pas un outil de plus à apprendre. C'est une couche de structure qui s'ajoute à ce que vous utilisez déjà.

- **Claude Code** — adaptateur natif inclus

Vos outils. Vos modèles. Votre méthode.

## En équipe : une cohérence plus accessible avec l'IA

En développement traditionnel, il est difficile d'obtenir dix développeurs qui codent à l'identique — et ce n'est pas forcément souhaitable. Chacun apporte son style, ses habitudes, ses préférences. Les conventions, linters et revues de code réduisent les écarts sans les effacer ; c'est ce qui fait aussi la richesse d'une équipe.

Avec l'IA et un cadre partagé comme Lytos, une partie de l'homogénéité peut devenir plus accessible — sans que les habitudes individuelles disparaissent.

Un manifest, des rules, des skills — partagés par l'équipe. Chaque développeur brainstorme, affine le besoin, valide le résultat. Une partie du code peut alors être produite avec le même contexte, les mêmes contraintes, les mêmes procédures.

Le résultat : un projet où les différences de forme se réduisent, pendant que les différences de jugement continuent de faire la valeur des humains qui l'écrivent.

> *"Le développeur brainstorme. Lytos aide à harmoniser."*

Le rôle du développeur se recentre sur ce que l'IA fait mal : définir le besoin, challenger la proposition, valider. Lytos cherche à s'assurer que les lignes produites respectent l'identité du projet — comme un complément aux revues et conventions déjà en place.
