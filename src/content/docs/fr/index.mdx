## Le paradigme des sub-agents est une impasse

La majorité des frameworks IA actuels vous demandent de déléguer à des agents : un agent "architecte", un agent "testeur", un agent "reviewer". Plus vous déléguez, moins vous contrôlez. Le contexte s'éparpille. Les décisions s'opacifient. Vous perdez la main sur votre propre projet.

**Lytos fait le choix inverse.**

> *"L'agile a structuré la collaboration humaine. Lytos structure la collaboration avec l'IA."*

Pas d'agents autonomes. Pas de personas qui décident à votre place. L'IA reste un outil — puissant, mais dirigé. C'est vous qui définissez l'intention. C'est vous qui validez chaque étape. Le modèle exécute. Vous, vous gouvernez.

[Pourquoi les sub-agents sont une illusion →](/fr/method/sub-agents/)

## Votre IA recommence à zéro à chaque session

Sans structure, chaque conversation repart de zéro. Vous réexpliquez l'architecture. Vous rappelez les contraintes. Vous corrigez les mêmes erreurs. Le modèle génère du code générique, déconnecté de votre projet réel.

Le résultat : des heures perdues à recadrer, des incohérences qui s'accumulent, et une IA qui ne comprend jamais vraiment votre projet.

---

## Votre contexte vous appartient

Avec les outils cloud classiques, votre contexte projet vit dans leurs serveurs, dans leurs formats, dépendant de leurs APIs. Changer de modèle signifie tout recommencer.

Avec Lytos, tout est en Markdown dans votre dépôt Git. Votre manifest, vos standards, votre mémoire de projet : version-contrôlés, portables, lisibles par n'importe quel modèle.

Aujourd'hui Claude. Demain GPT ou Gemini. Votre contexte ne bouge pas.

> *"Choisissez votre IA. Ne lui appartenez pas."*

## 5 piliers. Une méthode complète.

Lytos structure votre collaboration avec l'IA en cinq couches qui s'emboîtent :

<CardGrid>
  <Card title="Intent" icon="document">
    Le manifeste de votre projet. Objectif, périmètre, décisions structurantes. L'IA sait *pourquoi* elle code, pas seulement *quoi* coder.
  </Card>
  <Card title="Design" icon="puzzle">
    Vos playbooks de session. Comment aborder une revue de code, une refacto, un déploiement. Des workflows reproductibles, adaptés à votre projet.
  </Card>
  <Card title="Standards" icon="approve-check">
    Vos règles de qualité. Taille de fichiers, nommage, couverture de tests, patterns interdits. L'IA respecte vos exigences sans qu'on ait à les répéter.
  </Card>
  <Card title="Progress" icon="rocket">
    Votre kanban Git-natif. Les tâches en cours, les décisions prises, l'historique des sprints. L'IA sait où en est le projet à chaque session.
  </Card>
  <Card title="Memory" icon="star">
    La mémoire vivante du projet. Architecture, bugs connus, patterns émergents, contexte métier. Ce que l'IA doit retenir d'une session à l'autre.
  </Card>
</CardGrid>

## Opérationnel en 2 minutes

```bash
npm install -g lytos-cli
lyt init
```

<img src={lytBoard.src} alt="lyt board — Le kanban Lytos dans le terminal" style="border-radius: 2px; border: 1px solid var(--lytos-ink-12); margin: 1.5rem 0;" />

`lyt init` génère la structure complète dans votre projet : `manifest.md`, `skills/`, `rules/`, `issue-board/`, `memory/`. Tout en Markdown. Tout dans votre repo.

| Commande | Ce qu'elle fait |
|----------|----------------|
| `lyt init` | Génère `.lytos/` (interactif, détecte votre stack) |
| `lyt board` | Régénère le kanban board |
| `lyt lint` | Valide la structure `.lytos/` |
| `lyt doctor` | Diagnostic complet avec score de santé |
| `lyt show` | Détail d'une issue avec progression |
| `lyt start` | Démarre une issue — branche, board, tout en une commande |
| `lyt close` | Ferme une issue — done, board, vérifie la checklist |

[Voir toutes les commandes sur npm →](https://www.npmjs.com/package/lytos-cli)

## Fonctionne avec votre setup actuel

Lytos n'est pas un outil de plus à apprendre. C'est une couche de structure qui s'ajoute à ce que vous utilisez déjà.

- **Claude Code** — adaptateur natif inclus
- **Cursor** — `.cursor/rules` généré automatiquement
- **OpenAI / GPT** — adaptateur system-prompt inclus
- **Gemini, Mistral, et tous les autres** — le Markdown est universel

Vos outils. Vos modèles. Votre méthode.

## En équipe : une cohérence impossible avant l'IA

En développement traditionnel, on ne peut pas demander à 10 développeurs de coder pareil. Chacun a son style, ses habitudes, ses préférences. Les conventions de code, les linters, les code reviews — tout ça réduit les écarts, mais ne les élimine jamais. Le code d'un projet à 5 développeurs a toujours 5 personnalités.

Avec l'IA + Lytos, c'est différent. **Pour la première fois, c'est possible.**

Un manifest, des rules, des skills — partagés par toute l'équipe. Chaque développeur brainstorme, affine le besoin, valide le résultat. Mais le code est produit par le même moteur, avec le même contexte, les mêmes contraintes, les mêmes procédures.

Le résultat : un projet à 10 développeurs qui a **une seule voix**. Pas parce qu'on a forcé des humains à coder pareil — mais parce que la structure garantit la cohérence.

> *"Le développeur brainstorme. Lytos harmonise."*

Le rôle du développeur change. Il ne tape plus du code toute la journée — il définit le besoin, il challenge l'IA, il valide. Et Lytos s'assure que chaque ligne produite respecte l'identité du projet.
