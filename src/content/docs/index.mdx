## What you lose every session

You switch models. You open a new session. You go from Claude to Codex.
And each time, the same ritual: re-supply the context, repeat the conventions, correct the same drifts.

Meanwhile, the debt sets in. Today's generated code no longer matches yesterday's. Conventions slip. The project grows faster than the AI's ability to find its way in it.

Many have come to accept this friction as normal. It isn't.

**Lytos addresses this by anchoring the context where it belongs: in the repo.**

| Profile | Typical setup | What Lytos brings |

## The limits of the sub-agent approach

Most current AI frameworks suggest delegating to agents: an "architect" agent, a "tester" agent, a "reviewer" agent. The more you delegate, the harder it becomes to keep the thread. Context scatters more easily, decisions become harder to trace.

**Lytos offers a complementary approach.**

No autonomous agents. No personas deciding for you. The AI stays a tool — powerful, but directed. You define the intent. You validate every step. The model executes. You govern.

[Why the sub-agent approach feels limited →](/en/method/sub-agents/)

## Your context belongs to you

With classic cloud tools, your project context lives on their servers, in their formats, dependent on their APIs. Switching models means starting over.

With Lytos, everything is Markdown in your Git repo. Your manifest, your standards, your project memory: version-controlled, portable, readable by any model.

Claude today. GPT or Gemini tomorrow. Your context doesn't move.

## Operational in 2 minutes

```bash
npm install -g lytos-cli
lyt init
```

<img src={lytBoard.src} alt="lyt board — Lytos kanban board in the terminal" style="border-radius: 2px; border: 1px solid var(--lytos-ink-12); margin: 1.5rem 0;" />

`lyt init` generates the complete structure in your project: `manifest.md`, `skills/`, `rules/`, `issue-board/`, `memory/`. Everything in Markdown. Everything in your repo.

| Command | What it does |
|---------|-------------|
| `lyt init` | Scaffold `.lytos/` (interactive, detects your stack) |
| `lyt board` | Regenerate the kanban board |
| `lyt lint` | Validate `.lytos/` structure |
| `lyt doctor` | Full diagnostic with health score |
| `lyt show` | Issue detail with progress bar |
| `lyt start` | Start an issue — branch, board, all in one command |
| `lyt close` | Close an issue — done, board, checks the checklist |

[See all commands on npm →](https://www.npmjs.com/package/lytos-cli)

## For teams: consistency that becomes more accessible with AI

In traditional development, it's hard to get ten developers to code identically — and it isn't always desirable. Each brings their own style, habits, preferences. Coding conventions, linters and code reviews reduce the gaps without erasing them; part of a team's richness comes from that variety.

With AI and a shared frame like Lytos, some of that homogeneity can become more accessible — without erasing individual habits.

One manifest, one set of rules, one set of skills — shared by the team. Each developer brainstorms, refines the requirements, validates the result. Part of the code can then be produced with the same context, the same constraints, the same procedures.

The result: a project where differences of form narrow, while differences of judgment continue to be what the humans who write it contribute.

> *"The developer brainstorms. Lytos helps harmonize."*

The developer's role recenters on what AI does poorly: defining the need, challenging the proposal, validating. Lytos aims to help each line produced respect the project's identity — as a complement to the reviews and conventions already in place.
