## The sub-agent paradigm is a dead end

Most current AI frameworks ask you to delegate to agents: an "architect" agent, a "tester" agent, a "reviewer" agent. The more you delegate, the less you control. Context scatters. Decisions become opaque. You lose control of your own project.

**Lytos makes the opposite choice.**

No autonomous agents. No personas deciding for you. The AI stays a tool — powerful, but directed. You define the intent. You validate every step. The model executes. You govern.

[Why sub-agents are an illusion →](/en/method/sub-agents/)

---

## Your AI starts from zero every session

Without structure, every conversation starts over. You re-explain the architecture. You repeat the constraints. You correct the same mistakes. The model generates generic code, disconnected from your real project.

The result: hours lost reframing, inconsistencies piling up, and an AI that never truly understands your project.

---

## Your context belongs to you

With classic cloud tools, your project context lives on their servers, in their formats, dependent on their APIs. Switching models means starting over.

With Lytos, everything is Markdown in your Git repo. Your manifest, your standards, your project memory: version-controlled, portable, readable by any model.

Claude today. GPT or Gemini tomorrow. Your context doesn't move.

[Learn more about sovereignty →](/en/philosophy/sovereignty/)

## Operational in 2 minutes

```bash
npm install -g lytos-cli
lyt init
```

<img src={lytosGif.src} alt="Lytos demo — lyt init, lyt board, lyt lint" style="border-radius: 8px; margin: 1.5rem 0;" />

<img src={lytBoard.src} alt="lyt board — Lytos kanban board in the terminal" style="border-radius: 8px; margin: 1.5rem 0;" />

`lyt init` generates the complete structure in your project: `manifest.md`, `skills/`, `rules/`, `issue-board/`, `memory/`. Everything in Markdown. Everything in your repo.

| Command | What it does |
|---------|-------------|
| `lyt init` | Scaffold `.lytos/` (interactive, detects your stack) |
| `lyt board` | Regenerate the kanban board |
| `lyt lint` | Validate `.lytos/` structure |
| `lyt doctor` | Full diagnostic with health score |
| `lyt show` | Issue detail with progress bar |
| `lyt start` | Start an issue — branch, board, all in one command |
| `lyt close` | Close an issue — done, board, checks the checklist |

[See all commands on npm →](https://www.npmjs.com/package/lytos-cli)

Your tools. Your models. Your method.

## For teams: consistency that was impossible before AI

In traditional development, you can't ask 10 developers to code the same way. Everyone has their style, their habits, their preferences. Coding conventions, linters, code reviews — they reduce gaps but never eliminate them. A project with 5 developers always has 5 personalities.

With AI + Lytos, it's different. **For the first time, it's possible.**

One manifest, one set of rules, one set of skills — shared by the whole team. Each developer brainstorms, refines the requirements, validates the result. But the code is produced by the same engine, with the same context, the same constraints, the same procedures.

The result: a 10-developer project that speaks **with one voice**. Not because you forced humans to code alike — but because structure guarantees consistency.

> *"The developer brainstorms. Lytos harmonizes."*

The developer's role changes. They don't type code all day — they define the need, they challenge the AI, they validate. And Lytos ensures every line produced respects the project's identity.
